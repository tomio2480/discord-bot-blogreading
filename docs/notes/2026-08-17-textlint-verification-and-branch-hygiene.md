2026-08-17 の 2 度目にあたるセッションで得た判断を記録する．

共通する教訓は「記録は当時の観測であり，現在の実体ではない」という点にある．

## 🔍 Issue の行番号と分類は陳腐化する

Issue #23 は PR #20 時点の行番号で対象を列挙していた．
その後 `CLAUDE.md` へ 4 行が追加され，行番号は下方向へずれていた．

ずれ自体は加算すれば追える．問題は分類のほうにあった．
Issue は 105 行と 107 行を「仕様引用部の全角括弧まわり」と書いていた．
実体は `set connpass [URL]` であり，半角角括弧の直前に置かれたスペースだった．
全角括弧は 1 文字も含まれていない．

74 行も同様である．Issue は `prh` による表記ゆれの指摘とだけ書いていた．
コードポイントを確認すると，長音記号 `ー`（U+30FC）ではなく
全角ハイフン `－`（U+FF0D）が入っていた．誤字でもあったのである．

Issue 本文は起票時点の観測を写したものにすぎない．
着手時は必ず現物へ当たり，行番号と分類の両方を取り直す．
件数の一致（今回は 7 件）は，取り直しが正しいことの手がかりになる．

## 🚦 lint の CI が通っても指摘 0 件とは限らない

`md-lint.yml` は中央テンプレの composite action を呼ぶ．
その中の reviewdog は `fail_on_error: false` で動く．
つまり指摘が何件あってもジョブは success で終わる．

`gh pr checks` の `pass` を根拠に「指摘 0 件」と報告してはならない．
確認は次の 2 つで行う．

- ジョブログに `.md:<行番号>` 形式の指摘行が現れないこと
- PR へ reviewdog の summary コメントが付いていないこと

PR #20 では summary コメントが付いていた．PR #26 では付かなかった．
この差が 0 件の根拠になる．なお `fail_on_error` の値はログの
`Markdown Lint via composite action` ステップに出力される．

## 🌿 remote-tracking ref は実体ではない

掃除の対象としてマージ済みブランチを 6 本挙げた．
根拠は `git branch -r --merged origin/main` の出力である．
しかし削除を試すと `remote ref does not exist` が返った．

5 本はマージ時に GitHub 側で自動削除されていた．
手元に残っていたのは古い remote-tracking ref だけである．
`git branch -r` はキャッシュを表示する．実体の問い合わせではない．

リモートの実体は `git ls-remote --heads origin` で確かめる．
掃除の前に `git remote prune origin` を通すと，この誤認は起きない．

## 📏 sentence-length は行の長さを見ていない

修正後の自己点検で，80 字を超える行が 2 本残った．
いずれも PR #20 の summary では指摘されていない行である．

`sentence-length` が数えるのは文であり，行ではない．
`．` で区切られた各文が上限未満なら，行が長くても通る．
行長で自己点検すると偽陽性が出る．文単位で区切ってから数える．

冒頭の英文は 1 文で 102 字あり，これは真の指摘だった．
`/init` が生成する定型文のため，文言は保つ判断とした．
`textlint-disable` と `textlint-enable` で該当行だけを挟み，
無効化の範囲を 1 行に閉じ込めている．ファイル全体では外さない．

## 🔤 文字化けする環境では誤字を判別できない

`－` の混入は，Git Bash 経由の出力では判別できなかった．
日本語がすべて化けるため，1 文字の違いは見えない．
PowerShell で読み直し，`[int]$_` でコードポイントを出して初めて確定した．

目視できない差異は，符号位置で確かめる．
この規律は `CLAUDE.md` の「出力が乱れたときの扱い」に既に書かれている．
今回はそれを実際に必要とした事例である．
